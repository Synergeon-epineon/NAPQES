## 1. Key Type and Format

### 1.1 Logical key format

A NAPQES symmetric key is an **ordered tuple** of K distinct prime integers:

```
key = (p_0, p_1, ..., p_{K-1})
```

where each `p_i` is a prime in `[1 000 000, 15 000 000]`.

**Recommended parameters:**
- K = 10 (default)
- Range: [1 000 000, 15 000 000]
- Provides ~2^196.6 classical key entropy (~2^98.3 post-Grover)

**Minimum acceptable parameters:**
- K = 7 (satisfies FIPS 198-1 §3: key length ≥ HMAC output length, i.e. ≥ 32 bytes)
- A 7-element key with 5-byte serialisation = 35 bytes = 280 bits > 256 bits

### 1.2 Serialised key format

The HMAC key material is derived by serialising the prime tuple:

```
key_bytes = be5(p_0) || be5(p_1) || ... || be5(p_{K-1})
```

where `be5(x)` is the 5 least-significant bytes of `x` in big-endian order.

For K = 10: `key_bytes` is 50 bytes (400 bits).

This serialised form is used as the HMAC key for all domain-separated
derivations. It is computed internally by `key_bytes()` in `rust/src/lib.rs`
and is never exposed through the public API.

## 2. Key Lifecycle

### 2.1 Key generation

Keys are generated using `generate_prime_numbers(count, min_val, max_val)`:

1. Initialise `rand::thread_rng()` (OS DRBG — see `DRBG_ATTESTATION.md`).
2. Draw a uniform random candidate from `[min_val, max_val]`.
3. Test for primality (trial division to sqrt; deterministic).
4. If prime and not already in the key, append to the key list.
5. Repeat until `count` primes are collected.

**CO responsibility:** The Crypto Officer is responsible for verifying that
key generation completes (does not panic), which requires a sufficiently wide
range to contain at least `count` distinct primes.

Callers may also supply externally generated prime tuples. The module does
not validate that supplied integers are prime; this is the caller's
responsibility.

### 2.2 Key entry

Keys enter the module via function parameters (`key: &[u64]`). The module
accepts any `&[u64]` slice. Input validation:

- The key must have at least 1 element (no explicit check; a zero-element
  key causes a panic in `key_bytes` due to an empty serialisation).
- The module does not verify that key elements are prime or distinct.

**Recommendation:** Always use `generate_prime_numbers` or verify externally
that all key elements are prime and distinct before passing to the module.

### 2.3 Key use

Keys are used only for:
- HMAC-SHA256 derivation (domain bytes 0x00–0x07).
- Authentication tag computation and verification.

A single key may be used for multiple encrypt/decrypt calls. Different
nonces ensure ciphertext independence across calls with the same key.

**Nonce reuse warning:** The module generates a fresh random nonce per
`encrypt_bytes` call. Using the same (key, nonce) pair for two different
plaintexts weakens IND-CPA security. The CRNG conditional test mitigates
catastrophic DRBG failure (consecutive equal nonces) but does not prevent
nonce reuse if the DRBG space is exhausted over a very long key lifetime.

**Key separation:** A single key MUST NOT be shared between different
applications or security domains. Use separate keys for each security
context.

### 2.4 Key storage

**The NAPQES Cryptographic Module does not provide key storage.** Key material
exists in process memory only for the duration of the function call. The
caller is responsible for:

- Protecting keys in memory (e.g., using OS-provided secure memory, locked
  pages, hardware-backed key stores).
- Restricting access to key material to authorised processes.
- Persisting keys through a key-wrapping mechanism (e.g., AES-KWP, or
  encrypting the key tuple with a master key stored in a HSM).

### 2.5 Key output

Keys generated by `generate_prime_numbers` are returned as `Vec<u64>` to
the caller. The module does not wrap or protect keys on output; the caller
must handle the key securely immediately after receipt.

The serialised `key_bytes` form is never output from the module. Only the
prime tuple is returned to the caller.

### 2.6 Key zeroization

When a key is no longer needed, the caller MUST invoke:

```rust
napqes::zeroize_key(&mut key);
```

The `zeroize_key` function overwrites each element of the key slice with
zero using `ptr::write_volatile`, which prevents the compiler from eliding
the write as a dead-code optimisation. After this call:

- All elements of `key` are 0.
- The caller should drop the `Vec` or overwrite the slice storage.

**Timing:** Zeroization should occur as soon as the key is no longer
needed — before returning from the function that holds it, before a
context switch, or before any inter-process communication.

**Caveat:** `zeroize_key` erases the `key: &mut [u64]` array in the
caller's stack or heap. It does not erase copies of the key that may exist
in CPU registers, CPU cache lines, OS swap, or memory dumps. For highest
assurance, run the module in a process with locked memory pages and
disabled swap.

## 3. Key Strength and Lifecycle Limits

| Parameter | Value | Standard reference |
|---|---|---|
| Classical key entropy (K=10) | ~2^196.6 bits | SP 800-57 Pt 1 §5.6: key entropy ≥ security level |
| Post-quantum key entropy (Grover, K=10) | ~2^98.3 bits | SP 800-57 Pt 1 Rev 5 §5.6.3 |
| Authentication tag | 256 bits (128 post-Grover) | FIPS 198-1 |
| Minimum key size (FIPS 198-1 §3) | K ≥ 7 (35 bytes) | Satisfied by default K=10 |
| Maximum key lifetime | Not defined by the module | Caller-determined; rotate periodically |
| Maximum number of encrypt calls per key | Not defined | No key-material exhaustion risk for reasonable volumes; see nonce collision analysis in `DRBG_ATTESTATION.md §4.1` |

## 4. Key Agreement and Transport

The NAPQES Cryptographic Module does **not** implement key agreement or
key transport. Symmetric keys MUST be distributed to parties by an
out-of-band mechanism. Recommended approaches:

- **Static pre-shared key:** Provisioned at manufacture or deployment.
- **ECDH + HKDF:** Exchange ephemeral DH keys, derive NAPQES key via HKDF.
- **ML-KEM (FIPS 203):** Post-quantum key encapsulation, derive NAPQES key
  via a KDF. This is the recommended hybrid approach for post-quantum deployments.

When a KDF is used to derive the prime-tuple key from a master secret,
the KDF output MUST be used to select prime elements via rejection sampling
(as in `generate_prime_numbers`). Feeding raw KDF output as prime elements
without validation would produce invalid keys.

## 5. Multi-Party and Role-Based Key Policies

| Requirement | Current support | Note |
|---|---|---|
| Split knowledge (K-of-N) | Not implemented | Caller must implement at the key-distribution layer |
| Dual control | Not implemented | Caller responsibility |
